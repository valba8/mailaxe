# Contributing to Mailaxe

Thanks for your interest in Mailaxe! Mailaxe is an unofficial fork of [Aerion](https://github.com/hkdb/aerion), and **pull requests are welcome**: you don't need to ask for permission before working on something. Send the finished implementation and it will be reviewed.

> [!NOTE]
> Report Mailaxe problems here, not in the Aerion repository. If a bug also happens in the official Aerion builds, consider reporting it [upstream](https://github.com/hkdb/aerion/issues) too.

## Code of Conduct

By participating in this project, you agree to maintain a respectful and inclusive environment for everyone.

## Issues

There are two issue templates:

- **Bug report**: something doesn't work as expected.
- **Feature or UI change**: a new feature, an improvement to an existing one, or a visual/aesthetic change.

Search the [existing issues](https://github.com/valba8/aerion/issues) first. Opening an issue before a pull request is optional; it's useful when you want feedback on an idea before spending time on it.

## Pull Requests

1. Fork the repository and create a branch from `mailaxe` (the default branch). Use one branch per change: `fix/...` for bug fixes, `feature/...` for features, `ui/...` for visual changes.
2. Keep each pull request focused on **one** change. Several small PRs are reviewed (and merged) much faster than one big one.
3. Fill in the pull request template: what it changes, why, how you tested it, and screenshots for anything visual.
4. Make sure the checks below pass.

AI-assisted contributions are fine, as long as you have read, understood and tested the code you submit.

### Optional features need a setting

Mailaxe users chose an Aerion-like client, so new behavior must not surprise them:

- **New features and visual changes are optional.** Add a switch in **Settings** (usually **Settings → General**) and make it **off by default**, so the app looks and behaves as before unless the user turns it on.
- When a change replaces something that already exists (for example, hiding a button), the setting must default to the **current** behavior.
- Bug fixes don't need a setting.
- If two options conflict, make them mutually exclusive in the Settings UI.

A new setting usually touches these places (look at an existing one, such as `RowHoverActions`, and follow the same pattern):

| Layer | File |
|---|---|
| Storage key and Get/Set | `internal/settings/store.go` |
| Backend binding | `app/settings.go` |
| Frontend bindings (alphabetical order) | `frontend/wailsjs/go/app/App.js`, `App.d.ts` (regenerated by `wails build`) |
| Frontend store (keep `loadSettings` destructuring and `Promise.all` in the same order) | `frontend/src/lib/stores/settings.svelte.ts` |
| Load and save | `frontend/src/lib/components/settings/SettingsDialog.svelte` |
| Switch in the UI | `frontend/src/lib/components/settings/GeneralTab.svelte` (or the relevant tab) |
| Labels and descriptions | `frontend/src/lib/i18n/locales/*.json` |

### Translations

Every new user-visible text needs an i18n key. Add it at least to `en.json` (the fallback language); translating it into the other locales is appreciated. Corrections and new languages are welcome as regular pull requests; see the [Translation Guide](docs/LANGUAGE.md).

### Checks before submitting

```bash
go build ./... && go test ./...
```

```bash
cd frontend && npm run check && npm run lint
```

Also run the app (`wails dev`) and try your change, with the new setting both on and off.

### Never commit

- `.env`, `.env.local` or any OAuth client ID/secret, API key or token. Mailaxe is distributed **without** OAuth credentials.
- Build output (`build/bin/`, `*.exe`, `mailaxe` binaries) or unrelated generated files.

## Principles

Regardless of bug fix or feature implementation, all contributions must follow these principles:

- Security: always take a security-first approach
- Privacy: user privacy is a top priority
- Minimalist: always take the simplest approach and put forth best effort to have a clutter-free UI
- Lightweight: maintain one of the core values inherited from Aerion -- keep the app lightweight in all aspects
- Efficiency: battery life on laptops is also a top priority -- minimize unnecessary resource consumption
- Flexible: accommodate a reasonable range of mainstream user preferences through configurable options
- Keyboard: ensure new UI components, features, and flows are fully accessible via keyboard

## Coding Standards

### General

**if/else if/else:**

While there are instances of `else if` and `else` statements in the current code base. We are constantly refactoring them as we find them. In general, unless absolutely necessary which is very rare, don't use `else` and especially not long chains of `else if`.

Instead, use guard clause (w/ early returns) or switch statements.

### Go (Backend)

- Follow standard Go conventions and `gofmt`
- Use meaningful variable and function names
- Add comments for exported functions
- Handle errors explicitly (no silent failures)
- Use structured logging with zerolog, and pick the level by how often the line fires:
  - `info` — one line per operation that records a decision or outcome (a sync finished, an IDLE connection was replaced, a token was refreshed)
  - `debug` — anything per message, per IMAP command, per batch, per autosave, or on a timer
  - `warn` / `error` — something went wrong but the app carries on
- To see logs while developing: `AERION_LOG_LEVEL=info make dev` (or `debug`). Add `AERION_LOG_FILE=<path>` to also write them to a file (console format, 10 MB rollover to `<path>.1`). Built binaries take `--log-level` and `--log-file`. The default is `fatal`, so a plain `make dev` prints nothing.

```go
// Good
func (s *Store) GetMessageByID(id string) (*Message, error) {
    if id == "" {
        return nil, fmt.Errorf("message ID is required")
    }
    // ...
}

// Avoid
func (s *Store) Get(x string) *Message {
    // ...
}
```

### TypeScript/Svelte (Frontend)

- Use TypeScript for type safety
- Follow Svelte 5 patterns (runes, `$state`, `$derived`)
- Keep components focused and under 500 lines
- Use meaningful component and variable names

```svelte
<!-- Good -->
<script lang="ts">
  let { message, onDelete }: { message: Message; onDelete: () => void } = $props()
  let isExpanded = $state(false)
</script>

<!-- Avoid -->
<script>
  export let m
  let x = false
</script>
```

### Commit Messages

Use clear, descriptive commit messages:

```
feat: Add keyboard shortcut for archive (Ctrl+E)

- Added handler in App.svelte
- Updated keyboard.svelte.ts store
- Added tooltip to archive button

Closes #123
```

Prefixes:
- `feat:` New feature
- `fix:` Bug fix
- `docs:` Documentation changes
- `style:` Code style changes (formatting, etc.)
- `refactor:` Code refactoring
- `test:` Adding or updating tests
- `chore:` Maintenance tasks


## Testing

### Running Tests

```bash
# Go tests
go test ./...

# Frontend tests (if available)
cd frontend && npm test
```

### Writing Tests

- Write tests for new functionality
- Focus on critical paths and edge cases
- Use table-driven tests in Go where appropriate


## Getting Started

### Prerequisites

- **Go** 1.25 or later
- **Node.js** 20 or later
- **Wails** v2 CLI (`go install github.com/wailsapp/wails/v2/cmd/wails@v2.16.0`)
- **Git**

### Development Setup

```bash
git clone https://github.com/valba8/aerion.git mailaxe
cd mailaxe
cd frontend && npm install && cd ..
wails dev
```

If you want to test Gmail or Outlook sign-in, create your own OAuth client (see the [README](README.md#gmail-and-outlook-setup)) and either paste it into **Settings → Accounts → OAuth Credentials (advanced)** or put it in a git-ignored `.env.local` file (see [.env.example](.env.example)).

### Building

```bash
wails build -clean
```

See [docs/BUILD.md](docs/BUILD.md) for platform details.
